clustertrace

By Harry Winter · Python · Source on GitHub

A debugger for LLM agents that runs on your own machine. Instead of reading traces one at a time, it groups runs by what the agent actually did, so you can see which patterns fail.

Why I built it

A multi-step agent I was working on failed roughly 20% of the time, and reading individual traces didn’t explain why. Clustering runs by their execution signature made the failure modes obvious.

How it works

  • Traces are stored locally in SQLite with FTS5 full-text search.
  • Each run gets a signature from its normalised, run-length-collapsed span sequence; runs with the same signature form a cluster.
  • The cluster view shows count, failure rate, a sample trace, the longest common failure prefix and the top failing nodes.
  • A local dashboard on localhost:7777 has trace, cluster, search, metrics, failure and per-trace Gantt views.

Three ways to capture traces

  1. Decorators and helpers (@clustertrace.trace, span, tool_call): async-safe, nested via contextvars.
  2. SDK wrappers for Anthropic (including Bedrock and Vertex clients) and OpenAI, with no global monkey-patching.
  3. OpenTelemetry: an OTLP receiver (JSON and protobuf) and a span exporter that maps gen_ai.* attributes.

Extras

  • An MCP server with six read-only tools so coding assistants can query failures directly.
  • Prompt analysis comparing prompts from successful and dead-ended sessions, plus a prompt linter.
  • A Claude Code integration via a SessionStart hook and OTLP.
  • Sampling and skip options for production use.

Results

  • In the bundled 60-trace demo, two clusters cover 10 of 12 failures (83%) across 18 distinct execution patterns.
  • Decorator overhead is about 35 µs; the SQLite write dominates at about 5 ms on Linux/macOS.
  • The demo runs with no API spend: pip install clustertrace then clustertrace demo.

Built with

Python, SQLite (FTS5), OpenTelemetry, Anthropic SDK, OpenAI SDK, Model Context Protocol, TypeScript.
